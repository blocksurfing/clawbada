## Scope

Focused, single-contract extension campaign on `contracts/BattleArena.sol`. The 2026-04-15 campaign closed BattleArena to all 12 contracts at a green baseline; V3 S1 layers V3 dispute spam-defenses on top of the shipped H-01 challenge-window frame *without* rewriting the resolution path. S2 (on-chain `BattleResolver.replay()`) is roadmap, not in scope here.

V3 S1 surface added to `BattleArena.sol`:

1. **Per-bracket dispute windows** replacing the flat `DISPUTE_WINDOW = 5 minutes` constant — defaults 5 min Low / 30 min Mid / 1 hour High.
2. **Bonded disputes** — disputer must post a bond (default 10% of bracket stake: 250 / 1,000 / 5,000 $CLAW). Refunded if admin sides with disputer; slashed to Treasury (85/15 burn-dev) otherwise.
3. **Per-address rate limit** — max 5 disputes per rolling 24h window via `_disputeTimestamps[address]` (prune-then-push pattern, bounded array).
4. **Timelocked admin tuning** — `MIN_TUNING_DELAY = 24h` enforced on-chain via two-step `propose*` + `enact*` for both window and bond.
5. **Tightened admin-setter caps** — bond capped at 20% of bracket stake (was 50%); window capped tier-by-tier (1d Low / 3d Mid / 7d High).

## Detailed findings (Trust lens)

### T-01 — `setDisputeBond` cap reduced from 50% to 20% of bracket stake

**Severity**: Medium  
**Status**: Fixed in this campaign  
**File**: `contracts/BattleArena.sol` (`proposeDisputeBond`)

**Issue.** Original V3 S1 implementation capped admin-tunable dispute bonds at 50% of bracket stake (`maxBond = STAKE_BRACKETS[bracketIndex] / 2`). At High bracket this allows a 25,000 $CLAW bond, on top of the 50K stake at risk. Even though successful disputes refund the bond, the 25K opportunity cost discourages risk-averse legitimate disputers from challenging a corrupt or buggy resolver, allowing cheats to stand.

**Fix.** Cap reduced to 20% (`maxBond = STAKE_BRACKETS[bracketIndex] / 5`). Default 10% bonds (250 / 1,000 / 5,000 $CLAW) remain well within the new cap. Invalid bond amounts revert with `InvalidDisputeBond(newBond)`.

**Regression**: `test_V3_proposeDisputeBond_capped_at_20pct_of_stake` covers the cap at all three brackets and the zero-disable edge.

### T-02 — On-chain timelock on `setDisputeBond` and `setDisputeWindow`

**Severity**: Medium  
**Status**: Fixed in this campaign  
**File**: `contracts/BattleArena.sol` (`proposeDisputeWindow`/`enactDisputeWindow`, `proposeDisputeBond`/`enactDisputeBond`)

**Issue.** The 48h-proposal + 24h-delay tuning policy in `docs/runbooks/admin-roles.md` is off-chain only; the contract had no programmatic enforcement. A compromised multisig could enact malicious parameter changes in a single transaction before other signers could react via key rotation.

**Fix.** Replaced single-step `setDisputeWindow` / `setDisputeBond` with timelocked two-step:

- `proposeDisputeWindow(bracket, value)` validates bounds, stores pending value + proposal timestamp.
- `enactDisputeWindow(bracket)` requires `block.timestamp >= proposedAt + MIN_TUNING_DELAY` (24h), then applies + clears pending.
- Same shape for bond setters.
- Re-proposing before enact overwrites the pending value AND resets the delay timer (prevents pre-staging future enactments).
- New errors: `NoPendingChange(bracketIndex)`, `TuningDelayNotElapsed(bracketIndex, enactableAt)`.
- New events: `DisputeWindowProposed`, `DisputeBondProposed` (existing `*Set` events emitted on enact).
- Constructor defaults still set directly (one-time initialization); only changes from defaults require the timelock.

**Regression**: `test_V3_proposeAndEnactDisputeWindow_onlyAdmin`, `test_V3_proposeAndEnactDisputeBond_onlyAdmin`, `test_V3_timelock_enactBeforeDelay_reverts`, `test_V3_timelock_enactWithoutPropose_reverts`, `test_V3_timelock_repropose_resetsTimer`, `test_V3_timelock_enactClearsPending`.

### T-03 — Tiered max dispute window by bracket

**Severity**: Low  
**Status**: Fixed in this campaign  
**File**: `contracts/BattleArena.sol` (`proposeDisputeWindow`)

**Issue.** Original V3 S1 capped `disputeWindow[bracket]` at a flat 7 days at every bracket. A compromised admin could set `disputeWindows[Low] = 7 days`, locking Low-bracket payouts (default 5 min) for 168× normal duration. `finalizeBattle` is permissionless after the window so eventual payout is preserved, but the operational delay is large for low-stakes battles.

**Fix.** Max window tiered by bracket: Low 1 day / Mid 3 days / High 7 days. Aligns max-stall with stake size — high-value matches genuinely warrant longer dispute windows; low-value matches should clear quickly.

**Regression**: `test_V3_proposeDisputeWindow_tieredCapsByBracket` covers each bracket's cap.
